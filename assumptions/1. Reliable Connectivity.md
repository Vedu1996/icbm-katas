**Context**

The Local Edge Server processes high-priority local operations—such as entry validation at Turnstiles using a Local Cache—and ingests data from local components (Ticket Counters, Sensors, CV Edge Devices) via a Local MQTT Broker. Critical announcements are triggered from the Cloud via a dedicated tunnel, and local telemetry/event data is periodically synced upstream to the Cloud MQTT Broker.

**Assumption**

A dedicated, reliable, high-uptime wired network connection exists between the Local Edge Server and the Cloud. This link supports two-way communication: periodic batch synchronization of telemetry/events from the edge to the Cloud MQTT Broker, and real-time remote procedure calls (RPC over tunnel) from the Cloud Task Rules Engine down to the local Critical Announcements service. The physical location of the edge server can be assumed to be close to the ticketing counters.

**Risks and Mitigations**

* **Risk:** Network latency spikes or intermittent outages interrupt the periodic sync to the Cloud MQTT Broker.
* **Mitigation:** The Local Edge Server buffers events locally using disk-backed queues in the Local MQTT Broker during disconnection, retrying synchronization once the link stabilizes without blocking local entry points.


* **Risk:** Edge-to-Cloud tunnel failure delays RPC execution for critical announcements.
* **Mitigation:** Fall back to a local rules engine on the Edge Server to trigger emergency or priority PA announcements directly if the remote RPC connection drops.
